## Admin console — security/access hardening

Flagged during the admin console audit but deliberately held back, since each needs a product decision (not just implementation) before starting:

- **Admin roles/permissions.** Today every admin account has identical, all-or-nothing access — any admin can delete users, change plan pricing, or remove other admins (see `AdminAdminsPage.tsx`'s own warning banner). Needs a decision on what a "read-only" or "support" tier admin should and shouldn't be able to do before it can be built.
- **Shorter admin JWT expiry + token revocation.** Admin tokens are stateless with a flat 7-day expiry (`TokenService`, `createServices.ts`). Removing an admin (`AdminManagementController.remove`) doesn't invalidate their already-issued token — it stays valid for up to 7 days after removal. Needs a decision on the tradeoff between session length and how quickly a removed admin's access should actually stop.
- **2FA on admin login.** `AdminService.login` is password-only. Given this console can delete accounts and change billing tiers, TOTP or WebAuthn would meaningfully raise the bar — needs a decision on which second factor to support and the enrollment/recovery flow.
- **Tamper-evident audit log.** `admin_audit_log` rows are plain inserts with no hash chaining/checksum — a rogue admin with direct DB access could edit or delete past entries without a trace. Needs a decision on whether to hash-chain entries, ship them to an external append-only log, or both.

## Email handling audit, Aug 2026 — gaps

Found while reviewing email verification/validation. The top three were built directly (email verification with a "track + nudge, don't block" rollout — see migration `0017_email_verification.sql`, `AuthService.register`/`updateProfile`/`verifyEmail`/`resendVerificationEmail`, and `AppShell`'s banner; server-side format validation via `worker/src/utils/validation.ts`'s `isValidEmail`, applied on register/updateProfile/forgot-password; case-insensitive email storage/lookup via `normalizeEmail` + `UserRepository.findByEmail`'s `LOWER(email)` match, plus a one-time backfill in the same migration). The remaining ones need their own pass:

- ~~**Password-reset email-bombing has no rate limit.**~~ **Resolved.** `AuthController.forgotPassword` now checks `EmailVerificationIpLogRepository` (extended with a `"password-reset"` action alongside `"verify"`/`"resend"`) before doing anything else — 5 requests per IP per 60 minutes, checked ahead of even the email-format validation so probing for the limit can't be done for free with malformed input. Still purely IP-scoped, same inherent limitation as every rate limit in this codebase (an attacker rotating IPs isn't stopped by this alone), but closes the "spam one victim's inbox with one address, repeatedly, from one place" case.
- ~~**A Resend send failure can leak which emails are registered.**~~ **Resolved.** `requestPasswordReset` is designed to always return 200 whether or not the email matches an account, so the response can't be used to enumerate real users — but `EmailService.send()` threw a plain `Error` on a non-ok Resend response, uncaught, *after* the reset token was already stored, so a registered-but-unsendable address 500'd instead of the usual silent 200. Fixed by wrapping the send in a swallowed `.catch()`, same pattern already used by `register`/`updateProfile`/`resendVerificationEmail` for the verification email. Added a regression test covering the send-failure case.
- ~~**Sending domain isn't verified for deliverability.**~~ **Resolved.** This turned out to be the actual root cause of a real bug report — new signups on production were never receiving their verification email, because `onboarding@resend.dev` silently refuses to deliver to anyone but the Resend account's own address (a 403 that was only surfacing through the resend-verification button, see the `AuthService.resendVerificationEmail` fix below). Moved `resumelingo.com`'s DNS to Cloudflare, verified it in Resend (DKIM/SPF/MX all confirmed), and updated `RESEND_FROM_EMAIL` to `noreply@resumelingo.com`.
- ~~**Suspended accounts can still change email / trigger a reset.**~~ **Resolved.** `AuthService.login()` blocked a suspended account, but `updateProfile()` and `requestPasswordReset()` didn't check the `suspended` flag at all — a suspended user (or someone who'd compromised that account) could still change the email on file or request a password reset email. `updateProfile()` now throws `AuthError` for a suspended account (authenticated call, no enumeration concern in saying why); `requestPasswordReset()` now `return`s early for one, same "resolve silently, no observable difference from a non-existent email" treatment it already gives unregistered addresses. Added regression tests for both.
- ~~**Related, broader gap.**~~ **Resolved.** Turned out cheaper than expected: `requireAuth`/`optionalAuth` (`authMiddleware.ts`) already call `authService.getUserById()` on every authenticated request to attach the full user record via `c.set("user", ...)` — so checking the `suspended` flag that call already returns isn't an extra D1 read at all, just an extra `if`. No tradeoff needed after all. `requireAuth` now rejects a suspended account with 401 on every route it guards (not just login), closing the "JWT issued before suspension keeps working everywhere else" gap. `optionalAuth` treats a suspended session as anonymous instead (matches its own "never reject the request" contract). No dedicated test added — no existing pattern in this codebase for testing Hono middleware directly (every other middleware here is covered only by `tsc` + the routes that use it), so this stays consistent with that rather than introducing new test infrastructure for one middleware file.
- ~~**Verification token window / brute-force concern.**~~ **Resolved.** `VERIFICATION_TOKEN_TTL_MS` shortened from 24h to 1h (matches the reset-token window) — mainly to limit exposure if a link leaks through some other channel (forwarded mail, shared inbox, a scanner caching the URL), since the token itself (256-bit random, hashed at rest) was never realistically brute-forceable at any window length. Added IP-based rate limiting on `verify-email` (10 failed attempts / 15 min) and `resend-verification` (5 attempts / 60 min) via new `EmailVerificationIpLogRepository`, same record/count/prune pattern as `AdminLoginIpLogRepository` — closes the actual scripted-abuse gap the token entropy alone doesn't address.

## Product review, Aug 2026 — gaps and feature ideas

Sized and prioritized below (P0 = do now, P3 = low priority / needs more groundwork first). P0/P1 items are being acted on directly rather than just logged here.

- ~~**P0 — Custom Domain is sold as an active Premium feature with zero backend.**~~ **Resolved.** Turned out this wasn't actually oversold, just mislabeled: "Custom domain" referred to `ResumeRepository.generateBrandedSlug`'s already-shipped Premium perk — a `{subscriber name}-{resume title}` public link (e.g. `resumelingo.com/r/jordan-lee-software-engineer`) instead of the `{title}-{random6}` every other tier gets. Relabeled to "Branded resume link" in `subscriptionPlans.ts`/`Pricing.tsx` (and the live D1 `plans` table via `/admin/plans`) so it can't be mistaken for real DNS-level custom domain hosting. **Decision: real DNS-level "host on your own domain" will not be built** — no clear upside identified, and real downsides (verifying and being responsible for arbitrary third-party domains/certs, and the abuse surface of letting anyone point an outside domain at hosted content on this platform). Removed from `FuturePremium.tsx`'s roadmap entirely rather than left as "coming soon."
- ~~**P0 — Resume analytics oversells what's actually tracked.**~~ **Copy resolved.** The landing page's Features section used to promise "views, unique visitors, location, device, time on page, downloads, and referral source," but `resume_views` (`ResumeAnalyticsRepository`) only ever stored `resumeId` + `viewedAt` — no visitor identity, geo, device, or referrer columns exist. Scoped the copy down to what's real ("See how your resume is performing, with a running view count and trend over time") in the same pass that fixed Custom Domain above — this line just hadn't been struck through until now. **Still open, P3 — the real build.** Cloudflare Workers get country/ASN for free via `request.cf` with no extra API call, so location is cheap to add; device would need User-Agent parsing on each view; referral source is just capturing the `Referer` header; "unique visitors" needs a privacy-conscious dedup key (e.g. a daily hash of IP+resumeId, not raw IP storage). All of it is a `resume_views` migration (new nullable columns) + updating wherever `recordView` is called + new aggregation queries + Premium dashboard UI. Medium effort, well-bounded by the existing event-log table — not started, no live copy depends on it now, so this is a real feature addition rather than a fix.
- **P1 — Subscribers can't edit their own AI-generated Summary/bullets.** Already scoped above under "Subscriber-facing — resume content editing." Backend groundwork partially exists already (`ResumeService.update` accepts `generatedSummary`/`generatedBullets` directly and only regenerates when answers/achievements/profession/name/title change), so the real gaps are: (1) no `summaryManuallyEdited` flag, so a manual edit would get silently clobbered the next time someone edits Work Experience or answers a profession question; (2) no subscriber-facing UI for it at all today — only `AdminResumeEditPage.tsx` (support-only) exposes these fields. Medium effort: one migration, an update to `ResumeService.update`'s regeneration gate, a "reset to auto-generated" action, and a textarea/bullet-list UI on the subscriber's own Edit Resume page.
- ~~**P2 — No job-application tracker tied to resume versions.**~~ **Shipped.** `job_applications` table (migration `0015`), `JobApplicationRepository`/`Service`/`Controller`, `/job-applications` page (log an application, status dropdown, expandable edit panel, delete with confirm). Professional/Premium only (`assertJobApplicationTrackerAllowed`, same hard-gate treatment as Version History). 50-application cap per user with an 80%-of-cap warning banner, plus a "clean up applications older than 12 months" recommendation the user has to explicitly confirm — never automatic deletion.
- ~~**P2 — No re-engagement email loop.**~~ **Shipped.** Weekly (Monday) digest emailing each Professional/Premium subscriber their past 7 days of resume views, skipping anyone with zero resumes or zero views rather than sending an empty report. Opt-out/on-by-default per the resolved product decision, with a mandatory unsubscribe link in every email (CAN-SPAM requirement).
  - Migration `0016_view_digest_opt_out.sql` adds `users."viewDigestOptOut"` (default 0/receiving). `UserRepository.findEligibleForDigest()`/`setViewDigestOptOut()`; `AuthService.setViewDigestOptOut()`; `User.toPublicJSON()` now includes the flag.
  - `EmailService.sendViewDigestEmail()` — same raw-`fetch`-to-Resend pattern as `sendPasswordResetEmail`. `ViewDigestService` (new) orchestrates the run: `UserRepository.findEligibleForDigest()` → per user, `ResumeRepository.findAllForUser()` + `ResumeAnalyticsRepository.dailyViewCounts(resumeIds, 7)` (same source the Premium dashboard's view-trend chart uses) → skip zero-resume/zero-view users → sign a stateless unsubscribe JWT (`TokenService<UnsubscribeDigestTokenPayload>`, 180-day expiry, no DB storage needed) → send. Each user's send is wrapped individually so one failure doesn't stop the run.
  - **Scheduled execution** — `wrangler.jsonc` now has a `triggers.crons` entry (`"0 14 * * 1"`, every Monday); `worker/src/index.ts` now exports `{ fetch, scheduled }` instead of the bare Hono app — the app's first-ever background job.
  - **Unsubscribe** — `POST /api/auth/unsubscribe-digest` (public, no login) verifies the token and sets the opt-out flag. Deliberately a POST triggered by a button click on the client's `/unsubscribe` landing page (`UnsubscribePage.tsx`), not a bare GET link, so an email security scanner prefetching links can't silently unsubscribe users. Logged-in users can also toggle it directly from Profile → "Email preferences" (`PUT /api/auth/me/email-preferences`).
- ~~**P0 — Portfolio pages & personal branding tools is sold as a Premium feature with zero backend.**~~ **Resolved.** Unlike Custom Domain (which turned out to be real, just mislabeled), this one was genuinely unbuilt — no portfolio page, media hosting, or "personal branding tools" exist anywhere in the codebase. Removed from `subscriptionPlans.ts`/`Pricing.tsx`'s Premium feature list (replaced with "AI Career Coach," which is real and wasn't previously listed there) and dropped the "Career Portfolio" card from `FuturePremium.tsx`'s roadmap entirely. **Decision: not building a separate portfolio/personal-site feature** — a resume builder hosting projects, videos, and recommendations is a different product, with its own media-hosting and moderation surface, and doesn't make the actual resumes better. See "Personal links on the resume itself" below for the resume-native alternative, if wanted later.
- **P3 — Optional "Links" section on the public resume page.** Came up while discussing the Portfolio-pages removal above: a subscriber with a portfolio URL, GitHub, personal site, Behance, etc. today has nowhere to put it — `ResumeRecord` only has `contactLinkedIn`, no generic link field (the software-engineer profession's "GitHub" question is just a raw Q&A answer folded into generated bullet text, not a rendered clickable link). Lightweight, resume-native option if this comes up again: an optional "Links" section on the existing public resume page — a small list of label + URL pairs (e.g. "Portfolio," "GitHub," "Personal Site," "Other") the subscriber adds from Edit Resume, rendered as clickable links the same way LinkedIn is today. Small — one migration column (JSON array, same pattern as `experience`/`education`), a form editor on Edit Resume, a render addition per template. Not started; logged here since it's the natural next ask once Portfolio pages are off the table.
- **P3 — LinkedIn profile import.** Lower priority than it sounds: LinkedIn's official API doesn't grant broad profile/work-history access without a partner-level integration approval, so a real "Sign in with LinkedIn and pull my experience" flow isn't realistically buildable against the public API. The existing "Import an existing resume" (PDF/Word/text upload, AI-extracted) already covers the same end goal, since LinkedIn lets anyone export their own profile as a PDF — likely cheaper to add a one-line hint pointing users at LinkedIn's own "Save to PDF" export than to build a new integration.

## Edit Resume — split into tabs (follow-up to the "shorten the form" pass)

The quick win shipped: `Sharing`, `ATS Check`, `Recruiter Mode`, `References`, `Cover Letter`, and `Version History` now default closed (`defaultOpen={false}` on each `CollapsibleSection` in `ResumeEditPage.tsx`) instead of everything defaulting open — cuts the initial expanded-section count from 11/15 to 6/15, no restructuring. Mocked up three options (defaults-only, grouped-into-one-row, and tabs); tabs was the preferred direction but is meaningfully bigger than the other two since it changes the navigation model, not just default state. Scoped here rather than built, so this doesn't get lost:

- **Proposed tab split:** "Content" (Info, Template, Skills & Tools, Work Experience, Education, Highlights & Achievements, Generated Summary & Bullets, Additional Details), "Design & Sharing" (Sharing, Recruiter Mode, References, Cover Letter), "History" (Version History). ATS Check probably belongs with Content since it's a live check against what's in that tab, not a separate concern — needs a final call when this is actually built.
- **Real implementation snags identified, not just a layout change:** (1) `scrollToAtsCheck`'s "jump to this section" deep link currently just scrolls within one page — under tabs it needs to switch tabs first, then scroll. (2) "Expand all"/"Collapse all" (`forceOpen` signal) currently applies to every section on the page at once regardless of which is visible; under tabs that either needs to become per-tab, or stay global and silently expand sections on tabs the user isn't looking at — needs a decision. (3) The "X of Y sections complete" progress bar (`sectionProgress`) needs a call on whether it stays one global count across all tabs, or becomes per-tab — global is probably right (it's about the resume's overall completeness, not the tab), but worth confirming. (4) Confirm the on-blur autosave (`handleFormBlur`) still fires correctly for fields on a tab that isn't currently mounted — `CollapsibleSection` already only renders children while `open`, so an unmounted field can't autosave a change that hasn't happened yet, but worth explicitly testing the "edit on tab A, switch to tab B without blurring first" case doesn't drop an edit.
- Not tier-gated, not sized as P0-P3 (it's a UX/structure change, not a gap-fix) — pick this up whenever the quick win stops being enough.
