Original scope, for reference:

CJ's idea: a scheduled job that checks for "hacker or odd activity," with a report living in the Admin Console. Scoped in full per CJ's request ("scope it all... email alerts as well as reports will be my preferred vehicles"), including the prevention gaps that need to close first — CJ agreed with all recommendations below.

**Why this is the right next security piece.** Everything shipped in the Aug 2026 admin-hardening pass (2FA, hash-chained audit log, shortened JWT + revocation) is *prevention* or *tamper-evidence for admin actions*. Nothing today detects abuse aimed at subscribers or the signup funnel, and nothing summarizes it anywhere. This closes that gap.

**Audit of what already exists vs. what's missing, checked directly against the code:**
- `AdminAuditLogRepository` — durable, hash-chained, never pruned. Good raw material for admin-side anomalies (mass deletes, plan/pricing changes, login from a new IP) — nothing new to log here, just a new consumer that reads it.
- `AdminLoginIpLogRepository` and `EmailVerificationIpLogRepository` (covers subscriber login, verify, resend, password-reset) — these already throttle in real time (429 past a threshold), but every row is pruned as soon as its rate-limit window passes (`pruneOlderThan`). There's no history left a day later to build a report from. This is the central gap: the counters exist, the memory doesn't.
- **No throttle or logging at all on `/api/auth/register`.** Already flagged in the pinned "Bogus/unverified account protection" entry above — a script can create unlimited accounts today, and nothing would notice a burst from one IP.
- **No throttle or logging at all on password-protected public resume links** (`ResumeController`'s `accessPassword` check) — someone could script-guess a shared resume's password with zero friction and zero trace.

**Prevention gaps to close (CJ: "add as much prevention as I can" — these are blocking, not optional, since the report is only as good as what it can see):**
1. Registration: add the same IP-throttle pattern as login/verify/resend (`EmailVerificationIpLogRepository`, new `"register"` action) — e.g. 5/IP/hour, 429 past that. Doesn't stop an IP-rotating bot, same acknowledged limitation as every other IP-based throttle in this app; still closes the "one-click unlimited accounts" case. Turnstile (Cloudflare CAPTCHA, native to Workers, free) is the stronger single lever if CJ wants to also stop distributed bots, not just single-IP scripts — separate decision, doesn't block the rest of this.
2. Public resume password check: same throttle pattern, keyed by resume slug + IP (guessing one specific resume's password matters more here than a blanket per-IP count, since the attacker's goal is one target, not volume).

**New durable table: `security_events`.** Separate from the rate-limit tables above (which must stay short-lived — that's what makes them cheap to query on every request) — this is an append-only log written to *in addition to* the throttle check, whenever a threshold is actually crossed, not on every attempt. Columns: `id`, `type` (e.g. `login_brute_force`, `register_burst`, `public_resume_password_guessing`, `admin_anomaly`), `ip`, `detail` (JSON: email/resume slug/admin id as applicable), `severity` (`info`/`warning`/`critical`), `createdAt`. Never pruned — this is the actual history the report and alerts read from.

**Scheduled job.** New daily Cron Trigger alongside the existing weekly one in `wrangler.jsonc` (`triggers.crons` already supports multiple entries — today it's just `["0 14 * * 1"]` for the view digest). A new `SecurityMonitorService` (same shape as `ViewDigestService`) runs once a day: re-scans the last 24h of `security_events`, rolls them into a daily summary, and — this is the "prevention as much as I can" piece — also independently re-derives a couple of signals that don't depend on someone else's threshold having already fired, e.g. total registrations from any single IP in the last 24h even if each one individually stayed under the per-request throttle (a slow-drip bot could otherwise stay invisible forever). Anything crossing a severity threshold gets appended to `security_events` too, so the report and the email alert read from one consistent source.

**Email alerts.** Reuses `EmailService`'s existing pattern (`sendPaymentFailedEmail` etc. — swallowed-catch, doesn't blow up the whole cron run if send fails). Fires immediately when a `critical` event is written (not batched to the daily cron — e.g. a spike of 50+ failed logins in an hour shouldn't wait until tomorrow's summary), plus a rolled-up daily digest of everything at `warning` severity or below so CJ isn't pinged for every single 429. Sent to the admin account's own email (same recipient AdminService already has on file), reusing the unsubscribe/opt-out precedent isn't needed here since this is operational, not marketing email.

**Admin Console report page.** New page (`/admin/security-report` or folded into the existing `/admin/security` page as a new section) listing `security_events` — filterable by type/severity/date range, same table/search/sort conventions as every other admin list page this session touched (`AdminTemplatesPage.tsx`'s `.admin-search` pattern, `SortableHeader`). Each row's `detail` expands to the specific IP/account/resume involved. This is explicitly the drill-down surface, not the primary notification — the email alert is what's supposed to get CJ's attention in the moment.

**Open product decisions before/while building:**
1. Exact thresholds per signal (failed logins/IP/hour, registrations/IP/hour, password guesses/resume/hour) — proposed starting points above, tune after real traffic is seen.
2. Turnstile vs. IP-throttle-only for registration (see prevention item 1) — Turnstile is more work (new dependency, client-side widget, secret key in Workers env) but is the only lever here that survives IP rotation.
3. Whether `security_events` ever gets purged/archived long-term, or kept forever (it's small — one row per crossed threshold, not per request — so likely fine to keep indefinitely, but worth a stated retention decision rather than an implicit one).
4. Whether the admin-anomaly signals (mass deletes, new-IP admin login) get their own severity tuning separate from the subscriber-facing ones, since a false positive there is more disruptive (fewer, higher-stakes events).

**Honest framing, not oversold:** this is threshold-based heuristics against known abuse patterns, not machine-learning anomaly detection — appropriately scoped for a solo-admin app this size. IP-based signals share the same acknowledged limitation as the existing throttles: an attacker rotating IPs isn't stopped by counting alone. Call it "abuse/security signals," not "hacker detection," in any UI copy.

**Sizing:** comparable to the AI Resume Refresh nudge entry below — a new table + migration, a new service, a new cron consumer, a new email template, a new admin page, plus the two prevention throttles. Bigger than a quick add-on; not started, no code changes made yet.

## P1 — AI Resume Refresh nudge email (proposed, Sep 2026) — high priority, not yet started

CJ's idea: a periodic email that notices a resume has gone stale, offers a short list of relevant keywords the subscriber might have picked up experience with since they last touched it, and — if they say yes to one — writes an AI-generated bullet and gets it onto their resume. Marked high priority/"soon" per CJ, but explicitly scoped here rather than built yet, since it's a meaningfully bigger lift than anything shipped this session and has several open product decisions below that change the shape of the build.

**Why this is worth it (not just "sure, let's build it"):** every recurring email this app sends today is read-only — the weekly view digest reports a number, password reset/verification links just authenticate. This is the first one that would let a subscriber take an action from the email that changes their actual resume content, which is a genuinely different (and stickier) kind of touchpoint: it's a recurring, concrete demonstration of the thing they're paying for (AI keeping the resume current) instead of a passive notification.

**Trigger — reuse the existing staleness signal, don't invent a new one.** `DashboardController.ts` already computes `daysSinceUpdate` per resume for the Premium "stale resumes" widget (30-day threshold there). This feature is the same computation with a different threshold (120 days) and a different consumer (an email job, not a dashboard card) — no new staleness logic needed, just a new cron consumer of `resume.updatedAt`.

**Keyword source — the Skills & Tools suggestion catalog, not ATS Check.** My first pass at this assumed keywords would come from `recurringMissingKeywords` (ATS Check's missing-keyword log), but that's Premium-only and depends on the subscriber having already run a keyword check — no good for Starter/Professional or a Premium subscriber who's never used ATS Check. `SkillSuggestionRepository.findByProfession(resume.profession)` is a better fit: it's the same admin-curated, per-profession skill/tool catalog the Skills & Tools editor already suggests from, has no tier gate, and works from day one. The email would pick the top handful of that profession's suggested labels the subscriber hasn't already added to `resume.skillsAndTools`.

**The interactive part — lands on an in-app page, doesn't mutate from the email link itself.** Same reasoning as why unsubscribe is a POST from a landing page rather than a bare GET link (email scanners/prefetchers can trigger GETs): clicking a keyword in the email should open a confirm page in the app, not silently rewrite the resume. That page would ask one short follow-up question (e.g. "what's an example of something you did with {keyword}, and what came of it?") rather than jumping straight from "yes" to a finished bullet — a bare keyword confirmation is much thinner input than the Challenge/Action/Result triple the Achievements editor normally builds a bullet from, and skipping straight to generation risks a generic, weak bullet that undermines trust in the AI. The cleanest technical shape: this follow-up answer becomes a new `AchievementEntry` (Challenge templated from the keyword, Action/Result from the subscriber's answer) run through the existing `IContentGenerator` pipeline — no new generation logic, just a new entry point into the one that exists. The generated bullet should be shown to the subscriber to accept/edit before it's saved, not auto-committed.

**New pieces needed (not a small add-on):**
- Migration: a nullable `lastRefreshNudgeSentAt` column on `resumes` (or a new small table if a subscriber has several stale resumes at once — see open question below) so a resume isn't re-nudged every single cron run once past the threshold.
- A new cron-driven service mirroring `ViewDigestService`'s shape (walk eligible resumes, build the email, send, per-user try/catch) — likely needs a daily cron rather than the digest's fixed weekly slot, since a 120-day-per-resume window isn't tied to a calendar day the way "every Monday" is.
- A new signed token payload (same stateless pattern as `UnsubscribeDigestTokenPayload`) carrying `{ userId, resumeId, keyword, purpose }`, short-lived, used to authorize the landing page.
- A new email template (`EmailService`), a new landing/confirm page on the client, and a small controller/service for verifying the token, accepting the follow-up answer, generating the bullet, and saving it once approved.
- Unsubscribe/opt-out wiring — same CAN-SPAM requirement as the view digest.

**Open product decisions — need your call before/while building:**
1. **Tier availability.** All tiers, or Professional/Premium only (matching Version History/Job Tracker's gating)? Leaning toward all tiers since this reads more like an activation/retention lever than a premium perk, but that's your call.
2. **Repeat behavior.** If a subscriber ignores the email, does it fire again every 120 days indefinitely, or only once until they actually touch the resume (which would reset the clock naturally via `updatedAt`)? Recommend the latter — nagging risks the unsubscribe outcome this is trying to avoid.
3. **Multi-resume subscribers.** Professional/Premium accounts can have several resumes. One combined email covering all currently-stale resumes (like the digest bundles all view counts), or a separate email per stale resume? Recommend one combined email — less inbox noise.
4. **Auth on click-through.** Does the landing page require an active login (simplest, consistent with every other resume-editing surface), or does it need to work for someone clicking from a phone where they're not logged in (would need a magic-link-style auth grant scoped to that one resume/action)?
5. **Follow-up depth.** One free-text box ("what did you do, and what came of it") vs. the fuller Challenge/Action/Result structure the Achievements editor uses elsewhere? Simpler is probably better for an email-driven flow, but worth confirming against bullet quality once there's something to actually test.

Sizing: bigger than the view digest ("medium" effort) — comparable to a whole feature like Version History or the Job Applications tracker, not a quick follow-on. Not started; no code exists for this yet.

## Admin console — security/access hardening

Flagged during the admin console audit but deliberately held back, since each needs a product decision (not just implementation) before starting. Decided Aug 2026 (pre-launch security pass): solo admin today, so roles/permissions stays deferred; the other three don't depend on headcount and were built directly.

- **Admin roles/permissions — still deferred.** Today every admin account has identical, all-or-nothing access — any admin can delete users, change plan pricing, or remove other admins (see `AdminAdminsPage.tsx`'s own warning banner). Explicitly not worth building while there's only one admin account; revisit if/when a second admin is ever added. Needs a decision on what a "read-only" or "support" tier admin should and shouldn't be able to do before it can be built.
- ~~**Shorter admin JWT expiry + token revocation.**~~ **Resolved.** Expiry shortened 7d -> 12h. Turned out the "removal doesn't invalidate the token" half of this was already stale by the time it was checked — `requireAdminAuth` already looks the admin up by ID on every request, so a deleted admin's token was already rejected immediately (`adminRepository.delete()` is a real hard delete, no caching). The actual remaining gap was no way to revoke a *still-existing* admin's sessions early (e.g. a leaked token) — fixed with a `tokenVersion` column embedded in the JWT and checked against the DB on every request, plus a self-service "Sign out of all sessions" action (`/admin/security`).
- ~~**2FA on admin login.**~~ **Resolved.** Hand-rolled TOTP (RFC 6238, Web Crypto HMAC-SHA1 — no npm dependency, same "Workers-native over a Node-shaped library" reasoning as `jose` over `jsonwebtoken`) rather than WebAuthn — simpler enrollment/recovery story for a solo admin, and TOTP apps are near-universal. One-time backup codes generated at enrollment (critical here specifically because losing the authenticator device with no second admin to help would otherwise be a total lockout).
- ~~**Tamper-evident audit log.**~~ **Resolved.** Hash-chained (`admin_audit_log.hash`, SHA-256 of each row's fields + the previous row's hash) rather than shipped externally — keeps everything in D1, no new infra/vendor. `AdminAuditLogRepository.verifyChainIntegrity()` + a "Verify integrity" button recompute the chain on demand. Pre-migration rows can't be retroactively verified (no SHA-256 in plain SQLite to backfill with) — documented as a real limitation, not hidden.

## Email handling audit, Aug 2026 — gaps

Found while reviewing email verification/validation. The top three were built directly (email verification with a "track + nudge, don't block" rollout — see migration `0017_email_verification.sql`, `AuthService.register`/`updateProfile`/`verifyEmail`/`resendVerificationEmail`, and `AppShell`'s banner; server-side format validation via `worker/src/utils/validation.ts`'s `isValidEmail`, applied on register/updateProfile/forgot-password; case-insensitive email storage/lookup via `normalizeEmail` + `UserRepository.findByEmail`'s `LOWER(email)` match, plus a one-time backfill in the same migration). The remaining ones need their own pass:

- ~~**Password-reset email-bombing has no rate limit.**~~ **Resolved.** `AuthController.forgotPassword` now checks `EmailVerificationIpLogRepository` (extended with a `"password-reset"` action alongside `"verify"`/`"resend"`) before doing anything else — 5 requests per IP per 60 minutes, checked ahead of even the email-format validation so probing for the limit can't be done for free with malformed input. Still purely IP-scoped, same inherent limitation as every rate limit in this codebase (an attacker rotating IPs isn't stopped by this alone), but closes the "spam one victim's inbox with one address, repeatedly, from one place" case.
- ~~**A Resend send failure can leak which emails are registered.**~~ **Resolved.** `requestPasswordReset` is designed to always return 200 whether or not the email matches an account, so the response can't be used to enumerate real users — but `EmailService.send()` threw a plain `Error` on a non-ok Resend response, uncaught, *after* the reset token was already stored, so a registered-but-unsendable address 500'd instead of the usual silent 200. Fixed by wrapping the send in a swallowed `.catch()`, same pattern already used by `register`/`updateProfile`/`resendVerificationEmail` for the verification email. Added a regression test covering the send-failure case.
- ~~**Sending domain isn't verified for deliverability.**~~ **Resolved.** This turned out to be the actual root cause of a real bug report — new signups on production were never receiving their verification email, because `onboarding@resend.dev` silently refuses to deliver to anyone but the Resend account's own address (a 403 that was only surfacing through the resend-verification button, see the `AuthService.resendVerificationEmail` fix below). Moved `resumelingo.com`'s DNS to Cloudflare, verified it in Resend (DKIM/SPF/MX all confirmed), and updated `RESEND_FROM_EMAIL` to `noreply@resumelingo.com`.
- ~~**Suspended accounts can still change email / trigger a reset.**~~ **Resolved.** `AuthService.login()` blocked a suspended account, but `updateProfile()` and `requestPasswordReset()` didn't check the `suspended` flag at all — a suspended user (or someone who'd compromised that account) could still change the email on file or request a password reset email. `updateProfile()` now throws `AuthError` for a suspended account (authenticated call, no enumeration concern in saying why); `requestPasswordReset()` now `return`s early for one, same "resolve silently, no observable difference from a non-existent email" treatment it already gives unregistered addresses. Added regression tests for both.
- ~~**Related, broader gap.**~~ **Resolved.** Turned out cheaper than expected: `requireAuth`/`optionalAuth` (`authMiddleware.ts`) already call `authService.getUserById()` on every authenticated request to attach the full user record via `c.set("user", ...)` — so checking the `suspended` flag that call already returns isn't an extra D1 read at all, just an extra `if`. No tradeoff needed after all. `requireAuth` now rejects a suspended account with 401 on every route it guards (not just login), closing the "JWT issued before suspension keeps working everywhere else" gap. `optionalAuth` treats a suspended session as anonymous instead (matches its own "never reject the request" contract). No dedicated test added — no existing pattern in this codebase for testing Hono middleware directly (every other middleware here is covered only by `tsc` + the routes that use it), so this stays consistent with that rather than introducing new test infrastructure for one middleware file.
- ~~**Subscriber login had no rate limit.**~~ **Resolved.** Found during a pre-launch security pass, not part of the original email audit, but same family of gap: `AdminAuthController.login` has been IP-rate-limited since the admin console shipped, but `AuthController.login` (subscriber-facing) had nothing at all — bcrypt slows each individual guess, but that's not a substitute for capping attempts, so a known email address could be brute-forced with unlimited automated login attempts. Extended `EmailVerificationIpAction` with a `"login"` value (reusing the same table, no migration needed — `action` is a plain `TEXT` column, no `CHECK` constraint) — 10 failed attempts per IP per 15 minutes, failure-only like `verifyEmail` (a correct login doesn't count against the limit).
- ~~**Verification token window / brute-force concern.**~~ **Resolved.** `VERIFICATION_TOKEN_TTL_MS` shortened from 24h to 1h (matches the reset-token window) — mainly to limit exposure if a link leaks through some other channel (forwarded mail, shared inbox, a scanner caching the URL), since the token itself (256-bit random, hashed at rest) was never realistically brute-forceable at any window length. Added IP-based rate limiting on `verify-email` (10 failed attempts / 15 min) and `resend-verification` (5 attempts / 60 min) via new `EmailVerificationIpLogRepository`, same record/count/prune pattern as `AdminLoginIpLogRepository` — closes the actual scripted-abuse gap the token entropy alone doesn't address.

## Product review, Aug 2026 — gaps and feature ideas

Sized and prioritized below (P0 = do now, P3 = low priority / needs more groundwork first). P0/P1 items are being acted on directly rather than just logged here.

- ~~**P0 — Custom Domain is sold as an active Premium feature with zero backend.**~~ **Resolved.** Turned out this wasn't actually oversold, just mislabeled: "Custom domain" referred to `ResumeRepository.generateBrandedSlug`'s already-shipped Premium perk — a `{subscriber name}-{resume title}` public link (e.g. `resumelingo.com/r/jordan-lee-software-engineer`) instead of the `{title}-{random6}` every other tier gets. Relabeled to "Branded resume link" in `subscriptionPlans.ts`/`Pricing.tsx` (and the live D1 `plans` table via `/admin/plans`) so it can't be mistaken for real DNS-level custom domain hosting. **Decision: real DNS-level "host on your own domain" will not be built** — no clear upside identified, and real downsides (verifying and being responsible for arbitrary third-party domains/certs, and the abuse surface of letting anyone point an outside domain at hosted content on this platform). Removed from `FuturePremium.tsx`'s roadmap entirely rather than left as "coming soon."
- ~~**P0 — Resume analytics oversells what's actually tracked.**~~ **Copy resolved.** The landing page's Features section used to promise "views, unique visitors, location, device, time on page, downloads, and referral source," but `resume_views` (`ResumeAnalyticsRepository`) only ever stored `resumeId` + `viewedAt` — no visitor identity, geo, device, or referrer columns exist. Scoped the copy down to what's real ("See how your resume is performing, with a running view count and trend over time") in the same pass that fixed Custom Domain above — this line just hadn't been struck through until now. **Still open, P3 — the real build.** Cloudflare Workers get country/ASN for free via `request.cf` with no extra API call, so location is cheap to add; device would need User-Agent parsing on each view; referral source is just capturing the `Referer` header; "unique visitors" needs a privacy-conscious dedup key (e.g. a daily hash of IP+resumeId, not raw IP storage). All of it is a `resume_views` migration (new nullable columns) + updating wherever `recordView` is called + new aggregation queries + Premium dashboard UI. Medium effort, well-bounded by the existing event-log table — not started, no live copy depends on it now, so this is a real feature addition rather than a fix.
- ~~**P1 — Subscribers can't edit their own AI-generated Summary/bullets.**~~ **Shipped — this entry was stale.** The two items directly above under "Subscriber-facing — resume content editing" (direct Summary/bullets editing with the `summaryManuallyEdited` flag, and the "Regenerate" button) are exactly this feature, already marked Shipped there — this P1 line just never got struck through when that work landed. No longer open.
- ~~**P2 — No job-application tracker tied to resume versions.**~~ **Shipped.** `job_applications` table (migration `0015`), `JobApplicationRepository`/`Service`/`Controller`, `/job-applications` page (log an application, status dropdown, expandable edit panel, delete with confirm). Professional/Premium only (`assertJobApplicationTrackerAllowed`, same hard-gate treatment as Version History). 50-application cap per user with an 80%-of-cap warning banner, plus a "clean up applications older than 12 months" recommendation the user has to explicitly confirm — never automatic deletion.
- ~~**P2 — No re-engagement email loop.**~~ **Shipped.** Weekly (Monday) digest emailing each Professional/Premium subscriber their past 7 days of resume views, skipping anyone with zero resumes or zero views rather than sending an empty report. Opt-out/on-by-default per the resolved product decision, with a mandatory unsubscribe link in every email (CAN-SPAM requirement).
  - Migration `0016_view_digest_opt_out.sql` adds `users."viewDigestOptOut"` (default 0/receiving). `UserRepository.findEligibleForDigest()`/`setViewDigestOptOut()`; `AuthService.setViewDigestOptOut()`; `User.toPublicJSON()` now includes the flag.
  - `EmailService.sendViewDigestEmail()` — same raw-`fetch`-to-Resend pattern as `sendPasswordResetEmail`. `ViewDigestService` (new) orchestrates the run: `UserRepository.findEligibleForDigest()` → per user, `ResumeRepository.findAllForUser()` + `ResumeAnalyticsRepository.dailyViewCounts(resumeIds, 7)` (same source the Premium dashboard's view-trend chart uses) → skip zero-resume/zero-view users → sign a stateless unsubscribe JWT (`TokenService<UnsubscribeDigestTokenPayload>`, 180-day expiry, no DB storage needed) → send. Each user's send is wrapped individually so one failure doesn't stop the run.
  - **Scheduled execution** — `wrangler.jsonc` now has a `triggers.crons` entry (`"0 14 * * 1"`, every Monday); `worker/src/index.ts` now exports `{ fetch, scheduled }` instead of the bare Hono app — the app's first-ever background job.
  - **Unsubscribe** — `POST /api/auth/unsubscribe-digest` (public, no login) verifies the token and sets the opt-out flag. Deliberately a POST triggered by a button click on the client's `/unsubscribe` landing page (`UnsubscribePage.tsx`), not a bare GET link, so an email security scanner prefetching links can't silently unsubscribe users. Logged-in users can also toggle it directly from Profile → "Email preferences" (`PUT /api/auth/me/email-preferences`).
- ~~**P0 — Portfolio pages & personal branding tools is sold as a Premium feature with zero backend.**~~ **Resolved.** Unlike Custom Domain (which turned out to be real, just mislabeled), this one was genuinely unbuilt — no portfolio page, media hosting, or "personal branding tools" exist anywhere in the codebase. Removed from `subscriptionPlans.ts`/`Pricing.tsx`'s Premium feature list (replaced with "AI Career Coach," which is real and wasn't previously listed there) and dropped the "Career Portfolio" card from `FuturePremium.tsx`'s roadmap entirely. **Decision: not building a separate portfolio/personal-site feature** — a resume builder hosting projects, videos, and recommendations is a different product, with its own media-hosting and moderation surface, and doesn't make the actual resumes better. See "Personal links on the resume itself" below for the resume-native alternative, if wanted later.
- **P3 — Optional "Links" section on the public resume page.** Came up while discussing the Portfolio-pages removal above: a subscriber with a portfolio URL, GitHub, personal site, Behance, etc. today has nowhere to put it — `ResumeRecord` only has `contactLinkedIn`, no generic link field (the software-engineer profession's "GitHub" question is just a raw Q&A answer folded into generated bullet text, not a rendered clickable link). Lightweight, resume-native option if this comes up again: an optional "Links" section on the existing public resume page — a small list of label + URL pairs (e.g. "Portfolio," "GitHub," "Personal Site," "Other") the subscriber adds from Edit Resume, rendered as clickable links the same way LinkedIn is today. Small — one migration column (JSON array, same pattern as `experience`/`education`), a form editor on Edit Resume, a render addition per template. Not started; logged here since it's the natural next ask once Portfolio pages are off the table.
  - **Revisited Sep 2026** — prompted by "should the LinkedIn field just be a generic 'Social URL'?" **Decision: no, don't rename/genericize the LinkedIn field itself.** LinkedIn is the one platform recruiters and ATS systems actually expect on a resume by name; widening its label dilutes that for the common case to serve an edge case. Personal social media (Facebook, TikTok, Instagram) also cuts against standard professional-resume advice for most job seekers — a hiring manager clicking through to a personal account can surface protected-characteristic info (age, religion, family status, etc.), which is real discrimination-liability exposure for the employer. This "Links" section is the right home for that need instead: opt-in, clearly labeled, doesn't touch the one field everyone's scanning for.
  - **Mockup** (see `docs/design-mockups/links-section-mockup.png`): collapsed by default in the sidebar like every other optional section — costs no space until someone opts in. Expanded state is deliberately minimal compared to Awards/Experience's list editors — just a label dropdown + URL input + a small remove (×) per row, no move/duplicate/description fields, so it can't add much weight to the left column. Label presets: Portfolio, GitHub, Personal site, Instagram, Other (free-text label when "Other" is picked) — short enough to stay scannable rather than trying to name every platform. Would need a hard cap (4-5 links) so it can't turn into a link dump.
  - **Decision: not a build-now item.** No actual demand signal — this came from a self-check during the LinkedIn-field conversation, not a subscriber request. The real cost is bigger than the compact editor suggests: a new D1 column/migration, `ResumeService`/`ResumeRepository`/`ResumeController` wiring, a render addition across all ~13 template families in `ResumePreview.tsx` (the same sprawl the LinkedIn-placeholder bug just took real effort to trace through), plus the PDF export, plain-text export, and admin edit page. Worth revisiting alongside the "generic personal bio template" open question above, since that's the persona (athlete, artist, self-marketer) this would matter most to — building it before that broader question is settled risks building the wrong shape.
- **P3 — LinkedIn profile import.** Lower priority than it sounds: LinkedIn's official API doesn't grant broad profile/work-history access without a partner-level integration approval, so a real "Sign in with LinkedIn and pull my experience" flow isn't realistically buildable against the public API. The existing "Import an existing resume" (PDF/Word/text upload, AI-extracted) already covers the same end goal, since LinkedIn lets anyone export their own profile as a PDF — likely cheaper to add a one-line hint pointing users at LinkedIn's own "Save to PDF" export than to build a new integration.
- **P3 — QR code linking to the public resume.** Tried once already (`4a13173` "Add a QR code to the public resume view page", reverted 8 minutes later in `80b0daa`) — the revert was purely technical, not a verdict on the idea: the implementation piped every public resume's URL through a third-party image API (`api.qrserver.com`) because this environment's npm registry access was blocked at the time (`npm install qrcode` 403'd), and sending resume URLs to an outside service to render the code was flagged as an unresolved trade-off in the commit itself. A bundled JS QR library (`qrcode` on npm, generates client-side, no outbound call, no URL leakage) would remove that objection cleanly if this gets picked up again.
  - **Use case:** not useful for digital-to-digital sharing (email, LinkedIn, job portals — recipient already has a clickable link). Earns its value at the print/physical boundary — a career fair table, a printed resume handed to a hiring manager, a business card — where scanning beats typing a URL by hand.
  - **The differentiating angle, if built:** `resume_views` today only stores `resumeId` + `viewedAt` — no way to attribute a view to its source. A QR scan is indistinguishable from any other visit to the public link. The "scan → tracked view → visible in the subscriber's dashboard" story (something a plain paper resume can't offer) only works once views can be tagged by source, which is the same groundwork already scoped above under "Resume analytics oversells what's actually tracked" (P3). Sequence this after that, not before — a QR code that can't prove it was scanned is just a link with extra steps.
  - **Decision, Sep 2026:** not a build-now item. No evidence yet that subscribers print/hand out resumes in person (the actual demand signal this would need), and building it ahead of the analytics-attribution groundwork gets a shinier feature with a weaker story. Revisit alongside the analytics P3 item if either gets prioritized.
  - **Related smaller fix, not yet done:** `Features.tsx` and `FuturePremium.tsx` both still reference QR codes as if shipped/coming-soon, despite no QR feature existing in the app today — same "sold as a feature with zero backend" pattern already caught and fixed for Custom Domain and Portfolio pages above. Worth correcting regardless of the build decision.
- **Open question — generic "personal bio" template (athlete, artist, non-job-seeker self-marketing).** Raised Aug 2026: would a template for someone marketing themselves rather than applying for jobs (an athlete's or artist's bio page, no traditional job history) fit this product? Not previously scoped as a template. It's a narrower idea than the "Portfolio pages & personal branding tools" feature above, but leans on the same boundary — that item was explicitly rejected with **"not building a separate portfolio/personal-site feature"** (different product, own media-hosting/moderation surface, doesn't make actual resumes better). A bio template pushes on that same question from the template side: the current template system is built around profession-specific resume content (Work Experience, Skills & Tools, Generated Summary & Bullets), which doesn't map cleanly onto a non-job-seeker bio. The lighter-weight, already-scoped alternative is the "Optional Links section" item above (portfolio/GitHub/personal site links on the existing resume page) rather than a new template type. Needs a real product decision before any build — not started.
