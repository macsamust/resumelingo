# To Do — Later Consideration

## Admin console — security/access hardening

Flagged during the admin console audit but deliberately held back, since each needs a product decision (not just implementation) before starting:

- **Admin roles/permissions.** Today every admin account has identical, all-or-nothing access — any admin can delete users, change plan pricing, or remove other admins (see `AdminAdminsPage.tsx`'s own warning banner). Needs a decision on what a "read-only" or "support" tier admin should and shouldn't be able to do before it can be built.
- **Shorter admin JWT expiry + token revocation.** Admin tokens are stateless with a flat 7-day expiry (`TokenService`, `createServices.ts`). Removing an admin (`AdminManagementController.remove`) doesn't invalidate their already-issued token — it stays valid for up to 7 days after removal. Needs a decision on the tradeoff between session length and how quickly a removed admin's access should actually stop.
- **2FA on admin login.** `AdminService.login` is password-only. Given this console can delete accounts and change billing tiers, TOTP or WebAuthn would meaningfully raise the bar — needs a decision on which second factor to support and the enrollment/recovery flow.
- **Tamper-evident audit log.** `admin_audit_log` rows are plain inserts with no hash chaining/checksum — a rogue admin with direct DB access could edit or delete past entries without a trace. Needs a decision on whether to hash-chain entries, ship them to an external append-only log, or both.

## Subscriber-facing — resume content editing

- **Direct editing of the generated Summary/Objective/Profile text.** `generatedSummary` (labeled "Objective," "Summary," "Profile," etc. depending on template — see `templateStyles.ts`'s `summaryLabel`) is produced by a deterministic rule-based generator (`ContentGenerator.ts`) from profession + interview answers + achievements, and today only an admin can hand-edit it (added for support cases — see `AdminResumeEditPage.tsx`). Regular subscribers have no way to tweak the wording themselves. Recommended approach: add an editable field on the subscriber's own Edit Resume page, plus a `summaryManuallyEdited` flag so `ResumeService.update` stops silently regenerating over a manual edit when profession/answers/achievements/name/title change afterward — with a "reset to auto-generated" action to opt back in. Same treatment would apply to `generatedBullets`.
- **Multiple auto-generated variants to choose from.** Lower priority than direct editing, and more work: the generator is fully deterministic (no randomness, no AI call), so "regenerate" would produce identical output today. Real variants would need either several alternate phrasing templates per profession or an LLM-backed generator, neither of which exists in this codebase yet. Worth revisiting only if user feedback after shipping direct editing shows people want alternatives rather than just wanting to fix the wording themselves.

## Product review, Aug 2026 — gaps and feature ideas

Sized and prioritized below (P0 = do now, P3 = low priority / needs more groundwork first). P0/P1 items are being acted on directly rather than just logged here.

- ~~**P0 — Custom Domain is sold as an active Premium feature with zero backend.**~~ **Resolved.** Turned out this wasn't actually oversold, just mislabeled: "Custom domain" referred to `ResumeRepository.generateBrandedSlug`'s already-shipped Premium perk — a `{subscriber name}-{resume title}` public link (e.g. `resumelingo.com/r/jordan-lee-software-engineer`) instead of the `{title}-{random6}` every other tier gets. Relabeled to "Branded resume link" in `subscriptionPlans.ts`/`Pricing.tsx` (and the live D1 `plans` table via `/admin/plans`) so it can't be mistaken for real DNS-level custom domain hosting. A genuine "host on your own domain" build is still unbuilt and now sits on `FuturePremium.tsx`'s roadmap as "Your own domain" — that one would still need Cloudflare for SaaS (custom hostnames + managed TLS), a `customDomain` column + verification status on `Resume`, and admin/support tooling for when verification breaks, plus a decision on who bears the Cloudflare for SaaS cost.
- **P0 — Resume analytics oversells what's actually tracked.** The landing page's Features section promises "views, unique visitors, location, device, time on page, downloads, and referral source," but `resume_views` (`ResumeAnalyticsRepository`) only stores `resumeId` + `viewedAt` — no visitor identity, geo, device, or referrer columns exist. *Fix now:* scope the landing copy down to what's real (daily view counts + trend, which the Premium dashboard chart already does). *Real build later:* Cloudflare Workers get country/ASN for free via `request.cf` with no extra API call, so location is cheap to add; device would need User-Agent parsing on each view; referral source is just capturing the `Referer` header; "unique visitors" needs a privacy-conscious dedup key (e.g. a daily hash of IP+resumeId, not raw IP storage). All of it is a `resume_views` migration (new nullable columns) + updating wherever `recordView` is called + new aggregation queries + Premium dashboard UI. Medium effort, well-bounded by the existing event-log table.
- **P1 — Subscribers can't edit their own AI-generated Summary/bullets.** Already scoped above under "Subscriber-facing — resume content editing." Backend groundwork partially exists already (`ResumeService.update` accepts `generatedSummary`/`generatedBullets` directly and only regenerates when answers/achievements/profession/name/title change), so the real gaps are: (1) no `summaryManuallyEdited` flag, so a manual edit would get silently clobbered the next time someone edits Work Experience or answers a profession question; (2) no subscriber-facing UI for it at all today — only `AdminResumeEditPage.tsx` (support-only) exposes these fields. Medium effort: one migration, an update to `ResumeService.update`'s regeneration gate, a "reset to auto-generated" action, and a textarea/bullet-list UI on the subscriber's own Edit Resume page.
- ~~**P2 — No job-application tracker tied to resume versions.**~~ **Shipped.** `job_applications` table (migration `0015`), `JobApplicationRepository`/`Service`/`Controller`, `/job-applications` page (log an application, status dropdown, expandable edit panel, delete with confirm). Professional/Premium only (`assertJobApplicationTrackerAllowed`, same hard-gate treatment as Version History). 50-application cap per user with an 80%-of-cap warning banner, plus a "clean up applications older than 12 months" recommendation the user has to explicitly confirm — never automatic deletion.
- **P2 — No re-engagement email loop.** Scoped in detail (Aug 2026) but not started — logged here per explicit instruction rather than building now, since the cadence/tier-eligibility/opt-in-default decisions below were left open.
  - **What's reusable:** `EmailService` already sends one email today (password reset, inline-HTML template via raw `fetch` to Resend — no SDK) — a digest is the same pattern, a new method alongside `sendPasswordResetEmail`. `ResumeAnalyticsRepository.dailyViewCounts(resumeIds, days)` already aggregates per-resume daily view counts; summing it per user gets "N views this week" without new aggregation logic. (`recentViews()` is *not* the right source — it's pre-filtered to Recruiter-Mode-enabled resumes only, for the dashboard's NotificationBell.)
  - **What's fully new:** (1) **Scheduled execution** — this Worker has no `crons` entry in `wrangler.jsonc` and no `scheduled` export in `index.ts` today (it's just `export default app`); this would be the app's first-ever background job, needing `export default { fetch: app.fetch, scheduled: ... }` instead. (2) **Email preferences** — `users` has no opt-out/notification-preference column at all; needs a migration + `UserRepository` method + a settings-page checkbox, and a token-based unsubscribe endpoint (no login required, since it's reached from an email link) — this isn't optional, it's a CAN-SPAM requirement for any recurring marketing-ish email. (3) **Digest orchestration** — a new service that, on the cron tick, walks eligible users, sums their view counts, skips anyone with nothing to report, and calls `EmailService` per user in sensibly-sized batches so one Worker invocation doesn't time out on a large user base.
  - **Open product decisions, still unanswered — needed before implementation starts:** cadence (weekly vs. daily — weekly is far lower spam/annoyance risk and most days would have zero new views to report anyway); tier eligibility (every subscriber, vs. Professional/Premium only to match the precedent just set with Job Applications and with Resume Analytics' own dashboard display already being a paid perk); default state (opt-out/on-by-default vs. opt-in/off-by-default — opt-out reaches far more people but needs a clear unsubscribe link either way).
  - Medium effort overall, well-bounded by the existing `EmailService`/`ResumeAnalyticsRepository` pieces — the scheduled-execution and email-preference plumbing are the two genuinely net-new chunks of work.
- **P3 — LinkedIn profile import.** Lower priority than it sounds: LinkedIn's official API doesn't grant broad profile/work-history access without a partner-level integration approval, so a real "Sign in with LinkedIn and pull my experience" flow isn't realistically buildable against the public API. The existing "Import an existing resume" (PDF/Word/text upload, AI-extracted) already covers the same end goal, since LinkedIn lets anyone export their own profile as a PDF — likely cheaper to add a one-line hint pointing users at LinkedIn's own "Save to PDF" export than to build a new integration.
